## Введение

Производственная практика проходила в ОГБУ «Челябинский региональный центр навигационно-информационных технологий». Организация занимается развитием навигационно-информационных технологий и цифровизацией транспортной инфраструктуры региона.

Во время прохождения практики была выявлена существенная проблема: отсутствие актуальной информации о загруженности общественного транспорта на остановках, что приводит к неэффективному планированию поездок пассажирами и затрудняет оптимизацию маршрутов и расписания для транспортных компаний. Существующие системы мониторинга либо отсутствуют, либо не предоставляют данных в реальном времени, что делает невозможным принятие оперативных решений.

Целью данной практики является создание системы мониторинга и прогнозирования загруженности общественного транспорта с использованием технологий компьютерного зрения, которая позволит в реальном времени отслеживать количество пассажиров на остановках, детектировать автобусы и строить прогнозы загруженности на основе исторических данных. Главная задача системы — предоставить пассажирам актуальную информацию о текущей загруженности остановок и прогнозы на ближайшие часы, а также обеспечить транспортные компании аналитическими данными для оптимизации работы транспорта.

Для достижения поставленной цели необходимо решить следующие задачи:
1. Проанализировать деятельность предприятия и выявить ключевые проблемы в процессе мониторинга общественного транспорта;
2. Выполнить анализ существующих решений и технологий для создания систем мониторинга транспорта;
3. Разработать требования к программному продукту;
4. Спроектировать архитектуру системы и структуру базы данных;
5. Разработать сервис компьютерного зрения для детекции людей и автобусов на видеопотоках;
6. Реализовать сервис прогнозирования загруженности на основе временных рядов;
7. Создать веб-интерфейс для пассажиров и аналитическую панель для транспортных компаний;
8. Выполнить тестирование и развертывание системы.

Система должна обеспечивать обработку видеопотоков с камер, установленных на остановках, в реальном времени, детекцию людей и автобусов с помощью моделей машинного обучения, хранение исторических данных о пассажиропотоке и построение прогнозов загруженности с учетом сезонности и временных паттернов.

## 1 Теоретическая часть

### 1.1 Анализ предприятия и существующих бизнес-процессов

ОГБУ «Челябинский региональный центр навигационно-информационных технологий» является государственным бюджетным учреждением, ответственным за развитие навигационно-информационных технологий в Челябинской области. Организация занимается внедрением современных ИТ-решений для оптимизации транспортной инфраструктуры, развитием систем навигации и информационного обеспечения пассажиров общественного транспорта.

Основные бизнес-процессы организации связаны с:
- Сбором и обработкой данных о работе общественного транспорта;
- Предоставлением информационных сервисов для пассажиров;
- Аналитикой пассажиропотоков для транспортных компаний;
- Интеграцией с системами видеонаблюдения и навигации.

В настоящее время мониторинг загруженности остановок осуществляется в основном вручную или с использованием устаревших систем, не обеспечивающих обработку данных в реальном времени и не предоставляющих прогнозных данных.

### 1.2 Анализ проблемы

В процессе прохождения практики был проведен анализ текущей ситуации с мониторингом общественного транспорта, который выявил следующие проблемы:

1. Отсутствие актуальной информации о загруженности остановок в реальном времени для пассажиров;
2. Невозможность прогнозирования загруженности для планирования поездок;
3. Отсутствие автоматизированного сбора данных о пассажиропотоке;
4. Неэффективное использование данных видеонаблюдения, установленных на остановках;
5. Отсутствие аналитических инструментов для транспортных компаний по оптимизации маршрутов;
6. Ручной сбор статистики, требующий значительных временных затрат.

Решение данных проблем требует создания автоматизированной системы, которая позволит:
• Автоматически собирать данные о количестве пассажиров на остановках с помощью компьютерного зрения;
• Предоставлять пассажирам актуальную информацию о текущей загруженности в реальном времени;
• Строить прогнозы загруженности на основе исторических данных;
• Обеспечивать транспортные компании аналитическими данными для принятия решений;
• Оптимизировать использование существующей инфраструктуры видеонаблюдения;
• Снизить затраты на ручной сбор и обработку данных.

### 1.3 Разработка требований к программному продукту

### 1.3.1 Общие требования

Система мониторинга и прогнозирования загруженности общественного транспорта должна обеспечивать:

• Обработку видеопотоков с камер, установленных на остановках, в реальном времени;
• Автоматическую детекцию людей и автобусов на видеокадрах с использованием технологий компьютерного зрения;
• Хранение исторических данных о пассажиропотоке с временными метками;
• Построение прогнозов загруженности на основе анализа временных рядов;
• Предоставление API для доступа к данным о текущей загруженности и прогнозам;
• Веб-интерфейс для пассажиров с отображением текущей загруженности и прогнозов;
• Аналитическую панель для транспортных компаний со статистикой и графиками;
• Высокую производительность обработки видеопотоков и масштабируемость системы;
• Надежное хранение данных с возможностью быстрого доступа к историческим данным.

### 1.3.2 Сценарии использования

Для лучшего понимания того, как различные пользователи будут взаимодействовать с системой, были разработаны основные сценарии использования.

**Сценарий использования пассажиром:**
• Пассажир открывает веб-интерфейс системы;
• Выбирает интересующую остановку из списка;
• Просматривает текущую загруженность остановки (количество людей, статус);
• Изучает прогноз загруженности на ближайшие 24 часа;
• Принимает решение о времени поездки на основе полученной информации.

**Сценарий использования диспетчером транспортной компании:**
• Диспетчер открывает аналитическую панель;
• Выбирает остановку и период для анализа;
• Просматривает статистику загруженности за выбранный период;
• Анализирует часы пиковой загруженности;
• Использует данные для оптимизации расписания и распределения транспорта.

**Сценарий работы системы (автоматический):**
• Система периодически получает снимки с камер, установленных на остановках;
• Обрабатывает кадры с помощью модели компьютерного зрения (YOLO);
• Детектирует людей и автобусы на кадрах;
• Сохраняет данные о количестве людей и обнаруженных автобусах в базу данных;
• Периодически пересчитывает прогнозы загруженности на основе накопленных данных;
• Обновляет информацию в веб-интерфейсе для пользователей.

### 1.3.3 Функциональные требования

**Сервис компьютерного зрения:**
• Детекция людей на видеокадрах с указанием координат;
• Детекция автобусов на видеокадрах;
• Подсчет количества людей в зоне остановки;
• Распознавание номеров автобусов (опционально, с использованием OCR);
• Визуализация результатов детекции на кадрах;
• Обработка видеопотоков в реальном времени через WebSocket.

**Сервис прогнозирования:**
• Анализ исторических данных о пассажиропотоке;
• Построение прогнозов на 24 часа вперед;
• Учет сезонности (дневной, недельной);
• Предоставление доверительных интервалов для прогнозов;
• Кэширование результатов прогнозирования для повышения производительности.

**API Gateway:**
• Единая точка доступа к сервисам системы;
• Маршрутизация запросов к соответствующим сервисам;
• API для получения текущей загруженности остановок;
• API для получения прогнозов загруженности;
• API для аналитики (статистика, часы пика);
• API для административного управления (добавление остановок, настройка камер).

**База данных:**
• Хранение информации об остановках (координаты, камеры, зоны детекции);
• Хранение данных о пассажиропотоке с временными метками;
• Хранение информации о детекциях автобусов;
• Хранение прогнозов загруженности;
• Поддержка эффективных запросов по временным рядам.

**Веб-интерфейс:**
• Отображение списка остановок;
• Показ текущей загруженности выбранной остановки;
• Визуализация прогнозов на графиках;
• Отображение аналитики для транспортных компаний;
• Административный интерфейс для управления остановками и камерами.

### 1.4 Анализ существующих аналогов

На рынке существует ряд решений для мониторинга общественного транспорта и пассажиропотока. Был проведен анализ наиболее популярных аналогов:

**1. Яндекс.Транспорт**
- Предоставляет информацию о местоположении транспорта в реальном времени;
- Интеграция с картами;
- Отсутствие данных о загруженности остановок;
- Отсутствие прогнозирования;
- Зависимость от внешнего сервиса.

**2. Google Maps Transit**
- Информация о маршрутах и расписании;
- Отсутствие данных о загруженности;
- Отсутствие прогнозирования;
- Зависимость от внешнего сервиса.

**3. Системы видеонаблюдения с аналитикой (Hikvision, Dahua)**
- Детекция людей и объектов;
- Сложность интеграции с внешними системами;
- Высокая стоимость лицензий;
- Ограниченные возможности прогнозирования;
- Сложность настройки под специфические задачи.

**4. Специализированные системы для транспорта (TrafficEye, SmartBus)**
- Комплексные решения для управления транспортом;
- Высокая стоимость внедрения;
- Сложность кастомизации;
- Зависимость от поставщика;
- Ограниченная доступность для небольших регионов.

**5. Системы на базе IoT-датчиков**
- Точный подсчет пассажиров;
- Высокая стоимость оборудования;
- Необходимость установки дополнительной инфраструктуры;
- Сложность обслуживания;
- Ограниченная масштабируемость.

В результате анализа было выявлено, что существующие решения не в полной мере удовлетворяют потребностям организации по следующим причинам:
• Высокая стоимость лицензий и оборудования;
• Отсутствие данных о загруженности остановок;
• Отсутствие прогнозирования загруженности;
• Сложность интеграции с существующей инфраструктурой видеонаблюдения;
• Зависимость от внешних сервисов;
• Ограниченная гибкость настройки под специфические требования.

Это подтвердило необходимость разработки собственной системы мониторинга, адаптированной под специфические требования организации и использующей существующую инфраструктуру видеонаблюдения.

### 1.5 Анализ архитектурных подходов

В ходе выбора подхода к проектированию архитектуры программной системы были рассмотрены следующие модели:

• **Монолитная архитектура** — традиционный подход, где все компоненты системы тесно связаны и развертываются как единое целое. Предлагает простоту разработки и отладки, но ограничивает возможности масштабирования и затрудняет внедрение изменений.

• **Микросервисная архитектура** — современный подход, разделяющий систему на независимые сервисы, каждый из которых выполняет определенную бизнес-задачу. Обеспечивает гибкость, изолированное развертывание и масштабирование, но усложняет управление системой в целом.

• **Бессерверная архитектура (Serverless)** — модель, где поставщик облачных услуг автоматически управляет выделением и масштабированием ресурсов, часто используется для FaaS (Function as a Service).

• **Событийно-ориентированная архитектура** — подход, основанный на асинхронной обработке событий через брокеры сообщений, обеспечивающий слабую связанность компонентов.

Для проведения более глубокого анализа рассмотренных архитектурных подходов была составлена следующая сравнительная таблица:

**Таблица 1 — Сравнение архитектурных подходов**

| Архитектура | Преимущества | Недостатки |
|------------|-------------|------------|
| Монолитная | - Простота разработки и развертывания<br>- Единая кодовая база<br>- Быстрое взаимодействие компонентов | - Затрудненное масштабирование<br>- Сложность поддержки при росте<br>- Ограниченная гибкость технологического стека |
| Микросервисная | - Независимость развертывания<br>- Гибкость технологического стека<br>- Лучшая отказоустойчивость<br>- Возможность независимого масштабирования | - Сложность управления системой в целом<br>- Накладные расходы на коммуникацию<br>- Распределенные транзакции |
| Серверлесс | - Автоматическое масштабирование<br>- Оплата только за использование<br>- Сниженная операционная нагрузка | - Задержка при "холодном" старте<br>- Ограничения времени выполнения<br>- Зависимость от поставщика услуг<br>- Сложность отладки |
| Событийно-ориентированная | - Слабая связанность компонентов<br>- Высокая масштабируемость<br>- Асинхронная обработка | - Сложность обеспечения порядка событий<br>- Потенциальные проблемы с консистентностью<br>- Сложность отладки распределенных систем |

В результате анализа для проекта системы мониторинга транспорта была выбрана микросервисная архитектура с API Gateway и использованием асинхронной обработки задач через Celery. Этот выбор обусловлен следующими факторами:

• Необходимость независимого масштабирования компонентов (особенно ресурсоемкого сервиса компьютерного зрения);
• Изоляция компонентов для повышения устойчивости системы;
• Гибкость в выборе технологий для разных компонентов;
• Возможность независимого развертывания и обновления сервисов;
• Необходимость асинхронной обработки видеопотоков для обеспечения производительности;
• Возможность параллельной обработки данных с нескольких остановок.

### 1.6 Анализ инструментов для хранения и обработки данных

Современные системы мониторинга транспорта, особенно использующие компьютерное зрение и временные ряды, требуют специализированных инструментов для хранения и обработки данных. В рамках проекта были рассмотрены различные подходы к хранению данных.

**Системы управления базами данных:**
• **PostgreSQL** — объектно-реляционная СУБД с открытым исходным кодом, поддерживающая расширения для работы с временными рядами (TimescaleDB).
• **MongoDB** — документоориентированная NoSQL база данных, удобная для работы с неструктурированными данными.
• **InfluxDB** — специализированная база данных для временных рядов, оптимизированная для хранения метрик и событий.
• **TimescaleDB** — расширение PostgreSQL, специально разработанное для работы с временными рядами.

**Инструменты для работы с временными рядами:**
• **TimescaleDB** — расширение PostgreSQL, обеспечивающее автоматическое партиционирование по времени и оптимизированные запросы.
• **InfluxDB** — специализированная база данных с встроенной поддержкой временных рядов и агрегаций.
• **ClickHouse** — колоночная СУБД с высокой производительностью для аналитических запросов.

**Инструменты для кэширования и очередей:**
• **Redis** — in-memory хранилище данных, используемое для кэширования и брокера сообщений.
• **RabbitMQ** — брокер сообщений для асинхронной обработки задач.
• **Apache Kafka** — распределенная платформа потоковой обработки данных.

### 1.8 Анализ подходов к обеспечению безопасности и контроля доступа

В рамках проектирования системы мониторинга транспорта был проведен анализ различных подходов к обеспечению безопасности. В первоначальном плане рассматривались следующие механизмы:

• **Базовая аутентификация** — простая схема HTTP-аутентификации с передачей учетных данных в заголовках.
• **JWT (JSON Web Token)** — стандарт для безопасной передачи утверждений между сторонами с возможностью проверки целостности.
• **OAuth 2.0** — протокол авторизации, позволяющий передать права на доступ к ресурсам третьей стороне.
• **API-ключи** — уникальные идентификаторы, используемые для аутентификации вызывающей стороны API.

**Таблица 4 — Сравнение механизмов аутентификации**

| Механизм | Преимущества | Недостатки |
|----------|-------------|------------|
| Базовая аутентификация | - Простота реализации<br>- Широкая поддержка | - Передача в открытом виде (без HTTPS)<br>- Отсутствие механизма выхода |
| JWT | - Stateless-архитектура<br>- Удобство передачи в заголовках<br>- Содержит полезные данные | - Нет встроенного механизма отзыва<br>- Потенциально большой размер<br>- Риски при неправильной реализации |
| OAuth 2.0 | - Делегированный доступ<br>- Индустриальный стандарт<br>- Различные потоки для разных сценариев | - Сложность реализации<br>- Избыточность для простых систем |
| API-ключи | - Простота реализации<br>- Удобны для интеграций | - Сложность управления<br>- Отсутствие стандартов передачи |

Однако, учитывая специфику проекта и начальный этап разработки, было принято решение реализовать систему без механизмов аутентификации в текущей версии. Такой подход обусловлен следующими факторами:

• **Внутреннее использование** — система предназначена для использования внутри организации или в рамках регионального проекта;
• **Публичная информация** — данные о загруженности остановок не являются конфиденциальными;
• **Приоритет функциональности** — на начальном этапе разработки приоритет отдается функциональности системы;
• **Простота использования** — максимальная доступность для всех пользователей без необходимости авторизации.

В последующих версиях системы планируется внедрение следующих механизмов безопасности:
• Базовая аутентификация для административного интерфейса;
• Система логирования действий пользователей;
• Резервное копирование базы данных;
• Защита API от злоупотреблений (rate limiting);
• Использование HTTPS для всех соединений.

Такой поэтапный подход к внедрению механизмов безопасности позволяет ускорить разработку и внедрение первой версии системы, не снижая при этом ее функциональность.

## 2 Практическая часть

### 2.1 Архитектура приложения

Система мониторинга и прогнозирования загруженности общественного транспорта реализована по микросервисной архитектуре, где каждый компонент выполняет свою функцию. Взаимодействие между компонентами происходит через HTTP API и асинхронные задачи через Celery.

**Компоненты системы:**

• **API Gateway** — единая точка входа для всех клиентских запросов. Выполняет маршрутизацию запросов к соответствующим сервисам, обеспечивает базовый контроль доступа и координирует взаимодействие между компонентами системы. Реализован на FastAPI.

• **Сервис компьютерного зрения** — ядро системы обработки видеопотоков. Использует модель YOLO для детекции людей и автобусов на видеокадрах, обрабатывает видеопотоки в реальном времени и сохраняет результаты детекции в базу данных. Интегрирован в API Gateway как модуль.

• **Сервис прогнозирования** — отвечает за построение прогнозов загруженности на основе исторических данных. Использует библиотеку Prophet для анализа временных рядов, учитывает сезонность и строит прогнозы на 24 часа вперед. Интегрирован в API Gateway как модуль.

• **Celery Worker** — воркер для асинхронной обработки задач. Выполняет периодические задачи по мониторингу остановок, обработке видеокадров и обновлению данных.

• **Celery Beat** — планировщик задач для Celery. Обеспечивает периодический запуск задач мониторинга остановок.

• **PostgreSQL Database с TimescaleDB** — хранилище данных, содержащее информацию об остановках, данные о пассажиропотоке с временными метками, информацию о детекциях автобусов и прогнозы загруженности. Использует расширение TimescaleDB для эффективной работы с временными рядами.

• **Redis** — используется как брокер сообщений для Celery и для кэширования результатов прогнозирования.

• **Frontend** — веб-интерфейс для пассажиров и аналитическая панель для транспортных компаний. Предоставляет визуализацию данных, графики прогнозов и статистику.

• **Nginx** — веб-сервер и обратный прокси, обслуживающий статические файлы frontend и проксирующий запросы к API Gateway.

**Преимущества выбранной архитектуры:**
• Масштабируемость — каждый компонент может быть масштабирован независимо в зависимости от нагрузки;
• Отказоустойчивость — сбой в одном компоненте не приводит к отказу всей системы;
• Гибкость разработки — команда может работать над разными компонентами независимо;
• Технологическая гибкость — для каждого компонента можно выбрать оптимальные технологии;
• Асинхронная обработка — тяжелые задачи обработки видео выполняются асинхронно, не блокируя основной API;
• Эффективная работа с временными рядами — использование TimescaleDB обеспечивает высокую производительность запросов к историческим данным.

### 2.2 Проектирование базы данных

Для хранения данных системы была спроектирована структура базы данных в PostgreSQL с использованием расширения TimescaleDB для эффективной работы с временными рядами.

**Основные сущности:**

**Таблица `stops` (Остановки):**
• `id` — уникальный идентификатор остановки, первичный ключ;
• `name` — название остановки;
• `latitude` — широта местоположения остановки;
• `longitude` — долгота местоположения остановки;
• `camera_id` — идентификатор камеры, установленной на остановке;
• `camera_url` — URL видеопотока с камеры (опционально);
• `yandex_map_url` — ссылка на Яндекс.Карты для отслеживания автобусов;
• `stop_zone_coords` — координаты зоны остановки на кадре в формате JSON;
• `original_resolution` — оригинальное разрешение камеры в формате JSON;
• `is_active` — флаг активности остановки;
• `created_at` — время создания записи.

**Таблица `load_data` (Данные о загруженности):**
• `id` — уникальный идентификатор записи, первичный ключ;
• `stop_id` — идентификатор остановки, внешний ключ;
• `timestamp` — временная метка измерения, индексируется для быстрого доступа;
• `people_count` — количество людей на остановке;
• `buses_detected` — количество автобусов, обнаруженных на остановке;
• `detection_data` — дополнительные данные детекции в формате JSON.

Таблица `load_data` преобразована в гипертаблицу TimescaleDB для эффективной работы с временными рядами.

**Таблица `bus_detections` (Детекции автобусов):**
• `id` — уникальный идентификатор детекции, первичный ключ;
• `stop_id` — идентификатор остановки, внешний ключ;
• `bus_number` — распознанный номер автобуса;
• `detected_at` — время детекции, индексируется;
• `confidence` — уверенность детекции автобуса;
• `bus_bbox` — координаты автобуса на кадре в формате JSON;
• `detection_data` — дополнительные данные детекции в формате JSON.

**Таблица `forecasts` (Прогнозы загруженности):**
• `id` — уникальный идентификатор прогноза, первичный ключ;
• `stop_id` — идентификатор остановки, внешний ключ;
• `forecast_time` — время прогноза, индексируется;
• `predicted_people_count` — прогнозируемое количество людей;
• `confidence_interval_lower` — нижняя граница доверительного интервала;
• `confidence_interval_upper` — верхняя граница доверительного интервала;
• `created_at` — время создания прогноза.

**Особенности реализации:**
• Использование TimescaleDB для таблицы `load_data` обеспечивает автоматическое партиционирование по времени и оптимизированные запросы к временным рядам;
• JSON-поля используются для хранения гибких структур данных (координаты зон, метаданные детекций);
• Индексы на временных полях обеспечивают быстрый доступ к данным за определенный период;
• Связи между таблицами через внешние ключи обеспечивают целостность данных.

Данная структура базы данных обеспечивает:
1. Эффективное хранение данных о пассажиропотоке с временными метками;
2. Быстрый доступ к историческим данным для построения прогнозов;
3. Гибкость в хранении дополнительных метаданных;
4. Простоту расширения для добавления новых функций.

### 2.3 Структура серверной части

Серверная часть системы состоит из нескольких основных компонентов: API Gateway, интегрированные сервисы компьютерного зрения и прогнозирования, а также асинхронные задачи для обработки видеопотоков.

### 2.3.1 API Gateway

API Gateway реализован на FastAPI и выполняет роль центральной точки доступа к системе. Он обеспечивает:

**CRUD-операции для остановок:**
• Получение списка остановок;
• Создание, обновление и удаление остановок;
• Получение информации об остановке.

**API для пассажиров:**
• Получение текущей загруженности остановки;

**API для аналитики:**

• Получение истории количества людей на остановке.

**API для компьютерного зрения:**

### 2.6 Развёртывание

Система развертывается с использованием Docker и Docker Compose, что обеспечивает консистентную среду выполнения на разных платформах и упрощает процесс установки.

### 2.6.1 Структура Docker-контейнеров

Каждый компонент системы запускается в отдельном контейнере:

• **postgres** — контейнер с СУБД PostgreSQL и расширением TimescaleDB
  - Базовый образ: `timescale/timescaledb:latest-pg15`
  - Порты: 5432:5432
  - Тома: `postgres_data` для хранения данных
  - Health check для проверки готовности базы данных

• **redis** — контейнер с Redis
  - Базовый образ: `redis:7-alpine`
  - Порты: 6379:6379
  - Health check для проверки работоспособности

• **api_gateway** — контейнер с API Gateway
  - Собирается из Dockerfile в директории `./backend`
  - Порты: 8000:8000
  - Зависимости: postgres, redis
  - Переменные окружения для подключения к БД и Redis

• **celery_worker** — контейнер с Celery Worker
  - Собирается из Dockerfile в директории `./backend`
  - Зависимости: postgres, redis
  - Выполняет асинхронные задачи обработки видеопотоков

• **celery_beat** — контейнер с Celery Beat
  - Собирается из Dockerfile в директории `./backend`
  - Зависимости: postgres, redis
  - Планирует периодические задачи мониторинга

• **nginx** — контейнер с Nginx
  - Базовый образ: `nginx:alpine`
  - Порты: 80:80
  - Обслуживает статические файлы frontend и проксирует запросы к API Gateway
  - Зависимости: api_gateway

### 2.6.2 Процесс развертывания

Для развертывания системы необходимо выполнить следующие шаги:

**Подготовка конфигурации:**
• Создание файла `.env` в директории `./backend` с необходимыми переменными окружения:
  - `DATABASE_URL` — строка подключения к PostgreSQL
  - `REDIS_URL` — строка подключения к Redis
  - `CELERY_BROKER_URL` — URL брокера для Celery
  - `CELERY_RESULT_BACKEND` — URL бэкенда результатов Celery

**Сборка и запуск контейнеров:**
Сборка и запуск контейнеров производится командой:
```bash
docker-compose up --build
```

Для запуска в фоновом режиме:
```bash
docker-compose up -d --build
```

**Инициализация базы данных:**
• Создание таблиц базы данных выполняется автоматически при первом запуске API Gateway;
• Преобразование таблицы `load_data` в гипертаблицу TimescaleDB выполняется через SQL-скрипт или Alembic миграции.

**Проверка работоспособности:**
• Доступность API Gateway через запросы к `http://localhost:8000/health`;
• Доступность веб-интерфейса по адресу `http://localhost`;
• Проверка документации API через `http://localhost:8000/docs`;
• Проверка выполнения задач Celery через логи контейнеров.

**Мониторинг и управление:**
• Просмотр логов контейнеров: `docker-compose logs -f [service_name]`;
• Остановка системы: `docker-compose down`;
• Перезапуск отдельных сервисов: `docker-compose restart [service_name]`;
• Просмотр статуса контейнеров: `docker-compose ps`.

Для мониторинга и управления системой в docker-compose.yml настроены:
• Health checks для контейнеров с базой данных и Redis;
• Логирование с ограничением размера файлов лога;
• Политика автоматического перезапуска контейнеров при сбоях;
• Тома для персистентного хранения данных базы данных.

• Улучшения алгоритмов прогнозирования с использованием более сложных моделей машинного обучения (LSTM, Transformer);
• Разработки мобильного приложения для пассажиров;
• Интеграции с системами управления транспортом для автоматической оптимизации маршрутов;
• Расширенной аналитики с использованием методов data mining;
• Реализации системы уведомлений для пассажиров о приближении транспорта.

Разработанная система демонстрирует эффективное применение современных технологий компьютерного зрения и машинного обучения для решения практических задач мониторинга общественного транспорта и может служить основой для дальнейшего развития информационных систем в сфере транспорта.
