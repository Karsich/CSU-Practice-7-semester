# Практическая часть и Заключение

## 2 Практическая часть

### 2.1 Архитектура приложения

Система мониторинга и прогнозирования загруженности общественного транспорта реализована по микросервисной архитектуре, где каждый компонент выполняет свою функцию. Взаимодействие между компонентами происходит через HTTP API и асинхронные задачи через Celery.

Ниже представлена диаграмма архитектуры приложения, которая наглядно отображает взаимосвязи между компонентами системы:

```
┌─────────────────┐         ┌─────────────────┐
│   Frontend      │────────▶│   Nginx         │
│   (HTML/JS)     │         │   (Reverse Proxy)│
└─────────────────┘         └────────┬────────┘
                                     │
                                     ▼
                            ┌─────────────────┐
                            │   API Gateway   │
                            │   (FastAPI)     │
                            └────────┬────────┘
                                     │
        ┌────────────────────────────┼────────────────────────────┐
        │                            │                            │
        ▼                            ▼                            ▼
┌───────────────┐          ┌───────────────┐          ┌───────────────┐
│ CV Service    │          │ Forecast      │          │ Database     │
│ (YOLO)        │          │ Service       │          │ (PostgreSQL  │
│               │          │ (Prophet)     │          │ +TimescaleDB)│
└───────────────┘          └───────────────┘          └───────────────┘
        │                            │                            │
        │                            │                            │
        └────────────────────────────┼────────────────────────────┘
                                     │
                                     ▼
                            ┌─────────────────┐
                            │   Redis         │
                            │   (Cache/Broker)│
                            └────────┬────────┘
                                     │
        ┌────────────────────────────┼────────────────────────────┐
        │                            │                            │
        ▼                            ▼                            ▼
┌───────────────┐          ┌───────────────┐          ┌───────────────┐
│ Celery Worker │          │ Celery Beat   │          │   Cameras     │
│ (Tasks)       │          │ (Scheduler)   │          │   (IS74)      │
└───────────────┘          └───────────────┘          └───────────────┘
```

**Компоненты системы:**

• **Frontend** — веб-интерфейс для пассажиров и аналитическая панель для транспортных компаний. Предоставляет визуализацию данных, графики прогнозов и статистику. Реализован на чистом JavaScript с использованием Chart.js для графиков и Bootstrap для UI-компонентов.

• **Nginx** — веб-сервер и обратный прокси, обслуживающий статические файлы frontend и проксирующий запросы к API Gateway.

• **API Gateway** — единая точка входа для всех клиентских запросов. Выполняет маршрутизацию запросов к соответствующим сервисам, обеспечивает базовый контроль доступа и координирует взаимодействие между компонентами системы. Реализован на FastAPI.

• **Сервис компьютерного зрения** — ядро системы обработки видеопотоков. Использует модель YOLO (YOLOv8) для детекции людей и автобусов на видеокадрах, обрабатывает видеопотоки в реальном времени и сохраняет результаты детекции в базу данных. Интегрирован в API Gateway как модуль.

• **Сервис прогнозирования** — отвечает за построение прогнозов загруженности на основе исторических данных. Использует библиотеку Prophet для анализа временных рядов, учитывает сезонность и строит прогнозы на 24 часа вперед. Интегрирован в API Gateway как модуль.

• **Celery Worker** — воркер для асинхронной обработки задач. Выполняет периодические задачи по мониторингу остановок, обработке видеокадров и обновлению данных.

• **Celery Beat** — планировщик задач для Celery. Обеспечивает периодический запуск задач мониторинга остановок (каждую минуту).

• **PostgreSQL Database с TimescaleDB** — хранилище данных, содержащее информацию об остановках, данные о пассажиропотоке с временными метками, информацию о детекциях автобусов и прогнозы загруженности. Использует расширение TimescaleDB для эффективной работы с временными рядами.

• **Redis** — используется как брокер сообщений для Celery и для кэширования результатов прогнозирования.

**Преимущества выбранной архитектуры:**
• Масштабируемость — каждый компонент может быть масштабирован независимо в зависимости от нагрузки;
• Отказоустойчивость — сбой в одном компоненте не приводит к отказу всей системы;
• Гибкость разработки — команда может работать над разными компонентами независимо;
• Технологическая гибкость — для каждого компонента можно выбрать оптимальные технологии;
• Асинхронная обработка — тяжелые задачи обработки видео выполняются асинхронно, не блокируя основной API;
• Эффективная работа с временными рядами — использование TimescaleDB обеспечивает высокую производительность запросов к историческим данным.

### 2.2 Проектирование базы данных

Для хранения данных системы была спроектирована структура базы данных в PostgreSQL с использованием расширения TimescaleDB для эффективной работы с временными рядами.

**Основные сущности:**

**Таблица `stops` (Остановки):**
• `id` — уникальный идентификатор остановки, первичный ключ;
• `name` — название остановки;
• `latitude` — широта местоположения остановки;
• `longitude` — долгота местоположения остановки;
• `camera_id` — идентификатор камеры, установленной на остановке (например, camera1, camera2, camera3);
• `camera_url` — URL видеопотока с камеры (опционально);
• `yandex_map_url` — ссылка на Яндекс.Карты для отслеживания автобусов;
• `stop_zone_coords` — координаты зоны остановки на кадре в формате JSON (массив точек для определения полигона зоны детекции);
• `original_resolution` — оригинальное разрешение камеры в формате JSON (например, {"width": 2688, "height": 1520});
• `is_active` — флаг активности остановки;
• `created_at` — время создания записи.

**Таблица `load_data` (Данные о загруженности):**
• `id` — уникальный идентификатор записи, первичный ключ;
• `stop_id` — идентификатор остановки, внешний ключ;
• `timestamp` — временная метка измерения, индексируется для быстрого доступа;
• `people_count` — количество людей на остановке;
• `buses_detected` — количество автобусов, обнаруженных на остановке;
• `detection_data` — дополнительные данные детекции в формате JSON (координаты детекций, зона остановки, история изменений).

Таблица `load_data` преобразована в гипертаблицу TimescaleDB для эффективной работы с временными рядами. Это обеспечивает автоматическое партиционирование по времени и оптимизированные запросы к историческим данным.

**Таблица `bus_detections` (Детекции автобусов):**
• `id` — уникальный идентификатор детекции, первичный ключ;
• `stop_id` — идентификатор остановки, внешний ключ;
• `bus_number` — распознанный номер автобуса (через OCR);
• `detected_at` — время детекции, индексируется;
• `confidence` — уверенность детекции автобуса;
• `bus_bbox` — координаты автобуса на кадре в формате JSON [x1, y1, x2, y2];
• `detection_data` — дополнительные данные детекции в формате JSON.

**Таблица `forecasts` (Прогнозы загруженности):**
• `id` — уникальный идентификатор прогноза, первичный ключ;
• `stop_id` — идентификатор остановки, внешний ключ;
• `forecast_time` — время прогноза, индексируется;
• `predicted_people_count` — прогнозируемое количество людей;
• `confidence_interval_lower` — нижняя граница доверительного интервала;
• `confidence_interval_upper` — верхняя граница доверительного интервала;
• `created_at` — время создания прогноза.

**ER-диаграмма базы данных:**

```
┌─────────────┐
│   stops     │
├─────────────┤
│ id (PK)     │
│ name        │
│ latitude    │
│ longitude   │
│ camera_id   │
│ camera_url  │
│ ...         │
└──────┬──────┘
       │
       │ 1:N
       │
       ├──────────────────┐
       │                  │
       ▼                  ▼
┌─────────────┐    ┌─────────────┐
│ load_data   │    │bus_detections│
├─────────────┤    ├─────────────┤
│ id (PK)     │    │ id (PK)     │
│ stop_id(FK) │    │ stop_id(FK) │
│ timestamp   │    │ bus_number  │
│ people_count│    │ detected_at │
│ buses_...   │    │ confidence  │
│ ...         │    │ ...         │
└─────────────┘    └─────────────┘
       │
       │ 1:N
       │
       ▼
┌─────────────┐
│ forecasts   │
├─────────────┤
│ id (PK)     │
│ stop_id(FK) │
│ forecast_...│
│ predicted_..│
│ ...         │
└─────────────┘
```

**Особенности реализации:**
• Использование TimescaleDB для таблицы `load_data` обеспечивает автоматическое партиционирование по времени и оптимизированные запросы к временным рядам;
• JSON-поля используются для хранения гибких структур данных (координаты зон, метаданные детекций, дополнительные параметры);
• Индексы на временных полях (`timestamp`, `detected_at`, `forecast_time`) обеспечивают быстрый доступ к данным за определенный период;
• Связи между таблицами через внешние ключи обеспечивают целостность данных;
• Поддержка высокого разрешения кадров (до 2688x1520 пикселей) для точной детекции маленьких объектов.

Данная структура базы данных обеспечивает:
1. Эффективное хранение данных о пассажиропотоке с временными метками;
2. Быстрый доступ к историческим данным для построения прогнозов;
3. Гибкость в хранении дополнительных метаданных детекций;
4. Простоту расширения для добавления новых функций;
5. Оптимизированную работу с временными рядами через TimescaleDB.

### 2.3 Структура серверной части

Серверная часть системы состоит из нескольких основных компонентов: API Gateway, интегрированные сервисы компьютерного зрения и прогнозирования, а также асинхронные задачи для обработки видеопотоков.

#### 2.3.1 API Gateway

API Gateway реализован на FastAPI и выполняет роль центральной точки доступа к системе. Он обеспечивает:

**CRUD-операции для остановок:**
• Получение списка остановок;
• Создание, обновление и удаление остановок;
• Получение информации об остановке.

**API для пассажиров:**
• Получение текущей загруженности остановки (`/api/v1/passengers/current-load/{stop_id}`);
• Получение прогноза загруженности на заданный период (`/api/v1/passengers/forecast/{stop_id}`);
• Получение списка всех активных остановок (`/api/v1/passengers/stops`).

**API для аналитики:**
• Получение статистики загруженности за период (`/api/v1/analytics/load-statistics/{stop_id}`);
• Определение часов пиковой загруженности (`/api/v1/analytics/peak-hours/{stop_id}`);
• Получение истории количества людей на остановке.

**API для компьютерного зрения:**
• Детекция объектов на загруженном изображении (`/api/v1/cv/detect`);
• Детекция с визуализацией результатов (`/api/v1/cv/detect-with-visualization`);
• Обработка кадра видеопотока (`/api/v1/cv/process-frame/{stop_id}`);
• WebSocket для обработки видеопотока в реальном времени.

**API для административного управления:**
• Создание и управление остановками (`/api/v1/admin/stops`);
• Настройка камер и зон детекции;
• Управление конфигурацией системы.

**Взаимодействие с базой данных:**
• Определение моделей данных через SQLAlchemy;
• Управление соединениями с базой данных;
• Выполнение запросов к PostgreSQL.

#### 2.3.2 Сервис компьютерного зрения

Сервис компьютерного зрения отвечает за наиболее ресурсоемкую часть системы — обработку видеокадров и детекцию объектов. Он реализует:

**Детекцию объектов:**
• Загрузка предобученной модели YOLO (YOLOv8s, YOLOv8m, YOLOv8n);
• Детекция людей на видеокадрах (класс 0 в COCO dataset);
• Детекция автобусов на видеокадрах (класс 5 в COCO dataset);
• Подсчет количества людей в заданной зоне остановки;
• Оптимизация для работы с HD кадрами (до 2688x1520 пикселей);
• Детекция маленьких объектов (люди размером 15x8 пикселей на полном кадре).

**Распознавание номеров автобусов:**
• Извлечение области с номером автобуса из кадра;
• Применение OCR (EasyOCR или Tesseract) для распознавания текста;
• Фильтрация и валидация распознанных номеров;
• Улучшение изображения для лучшего распознавания (CLAHE, бинаризация, увеличение резкости).

**Обработку видеокадров:**
• Получение снимков с камер через HTTP-запросы к IS74 CDN;
• Декодирование изображений с использованием OpenCV;
• Обработка кадров с учетом зон остановки;
• Сохранение результатов детекции в базу данных;
• Сглаживание результатов детекции для стабильности (медианное значение последних 5 кадров).

**Визуализацию результатов:**
• Отрисовка bounding boxes для детектированных объектов;
• Подписи с информацией о детекциях;
• Выделение зоны остановки на кадре;
• Отображение статистики на кадре.

**Диаграмма классов сервиса компьютерного зрения:**


**Особенности реализации:**
• Использование модели YOLOv8 для обеспечения высокой точности и скорости детекции;
• Кэширование модели для избежания повторной загрузки;
• Оптимизация обработки с использованием GPU (при наличии);
• Поддержка обработки кадров в реальном времени через WebSocket;
• Обработка ошибок при недоступности камер или некорректных данных;
• Адаптивный выбор размера изображения для детекции в зависимости от разрешения кадра;
• Использование низкого порога уверенности (0.05) для детекции маленьких объектов;
• Фильтрация по размеру и соотношению сторон для улучшения качества детекции.

**Алгоритм детекции:**
1. Получение кадра с камеры через HTTP-запрос;
2. Определение оптимального размера изображения для детекции (640, 1280 или 1920 пикселей);
3. Выполнение детекции через YOLO с низким порогом уверенности для маленьких объектов;
4. Фильтрация детекций по классам (люди, автобусы);
5. Фильтрация по размеру и соотношению сторон;
6. Подсчет объектов в зоне остановки;
7. Распознавание номеров автобусов через OCR;
8. Сохранение результатов в историю для сглаживания;
9. Возврат сглаженных значений (медианное значение последних 5 кадров).

#### 2.3.3 Сервис прогнозирования

Сервис прогнозирования отвечает за построение прогнозов загруженности на основе исторических данных. Он реализует:

**Подготовку данных временного ряда:**
• Получение исторических данных о пассажиропотоке из базы данных;
• Агрегация данных по часам для снижения шума;
• Формирование DataFrame для анализа в формате, требуемом Prophet.

**Построение прогнозов с использованием Prophet:**
• Настройка модели Prophet с учетом сезонности (дневной, недельной);
• Обучение модели на исторических данных;
• Генерация прогнозов на заданный период (по умолчанию 24 часа);
• Вычисление доверительных интервалов для оценки неопределенности прогноза.

**Кэширование результатов:**

• Обработка случаев с недостаточным количеством исторических данных (минимум 10 точек);

### 2.5 Реализация

Система реализована по микросервисной архитектуре с использованием современных инструментов разработки и методологий.

#### 2.5.1 API Gateway

API Gateway реализован на FastAPI и выполняет роль центральной точки доступа к системе. Он обеспечивает:

**Маршрутизацию запросов:**
• Разделение API на модули по функциональности (passengers, analytics, admin, cv, yandex_maps);
• Единая точка входа для всех клиентских запросов;
• Проксирование запросов к соответствующим сервисам.

**Управление данными:**
• CRUD-операции для остановок через SQLAlchemy;
• Валидация входных данных через Pydantic;
• Обработка ошибок и возврат структурированных ответов.

**Интеграцию с сервисами:**
• Вызов методов сервиса компьютерного зрения для обработки кадров;
• Вызов методов сервиса прогнозирования для построения прогнозов;
• Асинхронная обработка запросов для повышения производительности.

**Особенности реализации:**
• Использование dependency injection для управления сессиями базы данных;
• CORS middleware для поддержки запросов из браузера;
• Автоматическая генерация документации API через Swagger UI;
• Структурированное логирование для упрощения отладки;
• Поддержка WebSocket для обработки видеопотоков в реальном времени.

#### 2.5.2 Сервис компьютерного зрения

Сервис компьютерного зрения реализован как модуль в составе API Gateway и отвечает за обработку видеокадров. Он реализует:

**Инициализацию моделей:**
• Загрузка предобученной модели YOLO при старте приложения;
• Инициализация OCR-библиотек (EasyOCR, Tesseract) при наличии;
• Кэширование моделей для избежания повторной загрузки.

**Детекцию объектов:**
• Обработка кадров через модель YOLO;
• Фильтрация детекций по классам (люди, автобусы);
• Подсчет объектов в заданной зоне остановки;
• Вычисление координат bounding boxes;
• Оптимизация для работы с HD кадрами (адаптивный выбор размера изображения).

**Распознавание номеров автобусов:**
• Извлечение области с номером из кадра автобуса;
• Применение OCR для распознавания текста;
• Фильтрация результатов по шаблонам номеров;
• Валидация распознанных номеров;
• Улучшение изображения для лучшего распознавания (CLAHE, бинаризация, увеличение резкости).

**Особенности реализации:**
• Использование YOLOv8 для обеспечения высокой точности детекции;
• Оптимизация обработки с использованием GPU (при наличии);
• Обработка ошибок при недоступности камер;
• Поддержка различных форматов изображений;
• Визуализация результатов детекции для отладки;
• Сглаживание результатов для стабильности (медианное значение последних 5 кадров);
• Детекция маленьких объектов (люди размером 15x8 пикселей на полном кадре).

#### 2.5.3 Сервис прогнозирования

Сервис прогнозирования реализован как модуль в составе API Gateway и отвечает за построение прогнозов. Он реализует:

**Подготовку данных:**
• Получение исторических данных из базы данных за заданный период;
• Агрегация данных по часам для снижения шума;
• Формирование временного ряда в формате, требуемом Prophet.

**Построение прогнозов:**
• Настройка модели Prophet с учетом сезонности;
• Обучение модели на исторических данных;
• Генерация прогнозов на заданный период;
• Вычисление доверительных интервалов.

**Кэширование:**
• Сохранение результатов в базе данных;
• Кэширование в Redis для быстрого доступа;
• Обновление прогнозов при поступлении новых данных.

**Особенности реализации:**

• Обработка случаев с недостаточным количеством данных;
• Оптимизация вычислений для снижения времени построения прогнозов.

#### 2.5.4 Асинхронная обработка задач

Для асинхронной обработки видеопотоков и периодических задач используется Celery с Redis в качестве брокера сообщений.

**Задачи мониторинга:**
• `monitor_stop_passive_task` — пассивный мониторинг остановки: получение снимка с камеры через IS74 CDN, обработка кадра через YOLO, сохранение данных о количестве людей и автобусах;
• `monitor_all_stops_passive_task` — мониторинг всех активных остановок, запускается периодически через Celery Beat (каждую минуту);
• Сохранение данных о детекциях автобусов в отдельную таблицу `bus_detections`.

**Планировщик задач (Celery Beat):**
• Периодический запуск задач мониторинга остановок (каждую минуту);
• Обновление прогнозов загруженности;
• Очистка устаревших данных.

**Особенности реализации:**
• Асинхронная обработка задач для неблокирующей работы API;
• Распределение нагрузки между несколькими воркерами;
• Обработка ошибок и повторные попытки при сбоях;
• Логирование выполнения задач для мониторинга;
• Получение снимков с камер через HTTP-запросы к CDN IS74;
• Обработка ошибок при недоступности камер.

**Диаграмма последовательности обработки задачи мониторинга:**

```
Celery Beat → monitor_all_stops_passive_task
                │
                ├─→ Для каждой остановки:
                │     │
                │     ├─→ Получение снимка с камеры (HTTP)
                │     │
                │     ├─→ Декодирование изображения (OpenCV)
                │     │
                │     ├─→ Детекция объектов (YOLO)
                │     │
                │     ├─→ Подсчет людей в зоне остановки
                │     │
                │     ├─→ Распознавание номеров автобусов (OCR)
                │     │
                │     └─→ Сохранение данных в БД
                │
                └─→ Завершение задачи
```

### 2.6 Развёртывание

Система развертывается с использованием Docker и Docker Compose, что обеспечивает консистентную среду выполнения на разных платформах и упрощает процесс установки.

#### 2.6.1 Структура Docker-контейнеров

Каждый компонент системы запускается в отдельном контейнере:

• **postgres** — контейнер с СУБД PostgreSQL и расширением TimescaleDB
  - Базовый образ: `timescale/timescaledb:latest-pg15`
  - Порты: 5432:5432
  - Тома: `postgres_data` для хранения данных
  - Health check для проверки готовности базы данных

• **redis** — контейнер с Redis
  - Базовый образ: `redis:7-alpine`
  - Порты: 6379:6379
  - Health check для проверки работоспособности

• **api_gateway** — контейнер с API Gateway
  - Собирается из Dockerfile в директории `./backend`
  - Порты: 8000:8000
  - Зависимости: postgres, redis
  - Переменные окружения для подключения к БД и Redis
  - Автоматическая перезагрузка при изменении кода (--reload)

• **celery_worker** — контейнер с Celery Worker
  - Собирается из Dockerfile в директории `./backend`
  - Зависимости: postgres, redis
  - Выполняет асинхронные задачи обработки видеопотоков

• **celery_beat** — контейнер с Celery Beat
  - Собирается из Dockerfile в директории `./backend`
  - Зависимости: postgres, redis
  - Планирует периодические задачи мониторинга (каждую минуту)
  - Очистка файла расписания при запуске для избежания конфликтов

• **nginx** — контейнер с Nginx
  - Базовый образ: `nginx:alpine`
  - Порты: 80:80
  - Обслуживает статические файлы frontend и проксирует запросы к API Gateway
  - Зависимости: api_gateway

**Диаграмма развертывания:**

#### 2.6.2 Процесс развертывания

Для развертывания системы необходимо выполнить следующие шаги:

**Подготовка конфигурации:**
• Создание файла `.env` в директории `./backend` с необходимыми переменными окружения:
  - `DATABASE_URL` — строка подключения к PostgreSQL
  - `REDIS_URL` — строка подключения к Redis
  - `CELERY_BROKER_URL` — URL брокера для Celery
  - `CELERY_RESULT_BACKEND` — URL бэкенда результатов Celery
  - `YOLO_MODEL_PATH` — путь к модели YOLO (по умолчанию `yolov8s.pt`)
  - `CONFIDENCE_THRESHOLD` — порог уверенности для детекции

**Сборка и запуск контейнеров:**
Сборка и запуск контейнеров производится командой:
```bash
docker-compose up --build
```

Для запуска в фоновом режиме:
```bash
docker-compose up -d --build
```

**Инициализация базы данных:**
• Создание таблиц базы данных выполняется автоматически при первом запуске API Gateway через SQLAlchemy (`Base.metadata.create_all(bind=engine)`);
• Преобразование таблицы `load_data` в гипертаблицу TimescaleDB выполняется через SQL-скрипт или Alembic миграции.

**Проверка работоспособности:**
• Доступность API Gateway через запросы к `http://localhost:8000/health`;
• Доступность веб-интерфейса по адресу `http://localhost`;
• Проверка документации API через `http://localhost:8000/docs`;
• Проверка выполнения задач Celery через логи контейнеров:
  ```bash
  docker-compose logs -f celery_worker
  docker-compose logs -f celery_beat
  ```

**Мониторинг и управление:**
• Просмотр логов контейнеров: `docker-compose logs -f [service_name]`;
• Остановка системы: `docker-compose down`;
• Перезапуск отдельных сервисов: `docker-compose restart [service_name]`;
• Просмотр статуса контейнеров: `docker-compose ps`;
• Просмотр использования ресурсов: `docker stats`.

Для мониторинга и управления системой в docker-compose.yml настроены:
• Health checks для контейнеров с базой данных и Redis;
• Логирование с ограничением размера файлов лога;
• Политика автоматического перезапуска контейнеров при сбоях;
• Тома для персистентного хранения данных базы данных;
• Зависимости между сервисами для правильного порядка запуска.

**Основные результаты проделанной работы:**

• Разработана архитектура системы, состоящей из нескольких компонентов: API Gateway на базе FastAPI, сервис компьютерного зрения с использованием модели YOLO (YOLOv8), сервис прогнозирования на базе библиотеки Prophet, асинхронные задачи обработки видеопотоков через Celery, база данных PostgreSQL с расширением TimescaleDB для эффективной работы с временными рядами, Redis для кэширования и брокера сообщений, и веб-интерфейс на чистом JavaScript с использованием Chart.js и Bootstrap 5.

• Реализован сервис компьютерного зрения с использованием модели YOLO для детекции людей и автобусов на видеокадрах, что позволяет автоматически собирать данные о пассажиропотоке без ручного вмешательства. Система оптимизирована для работы с HD кадрами (до 2688x1520 пикселей) и способна детектировать маленькие объекты (люди размером 15x8 пикселей на полном кадре). Реализовано распознавание номеров автобусов через OCR (EasyOCR, Tesseract) с улучшением изображения для повышения точности распознавания.

• Создан сервис прогнозирования загруженности с использованием библиотеки Prophet, который строит прогнозы на 24 часа вперед с учетом дневной и недельной сезонности и временных паттернов. Система учитывает исторические данные за последние 30 дней и вычисляет доверительные интервалы для оценки неопределенности прогнозов.

• Разработан веб-интерфейс для пассажиров с отображением текущей загруженности остановок и прогнозов, а также аналитическая панель для транспортных компаний со статистикой и графиками. Интерфейс адаптивен и работает на различных устройствах, автоматически обновляет данные каждые 30 секунд и предоставляет интерактивные графики для анализа данных.

• Настроено контейнерное развертывание с использованием Docker и Docker Compose, что обеспечивает простоту установки и запуска системы на различных платформах. Все компоненты системы изолированы в отдельных контейнерах, что упрощает управление и масштабирование.

• Реализована асинхронная обработка видеопотоков через Celery, что обеспечивает высокую производительность системы и возможность масштабирования. Система автоматически получает снимки с камер через HTTP-запросы к CDN IS74 каждую минуту, обрабатывает их через YOLO и сохраняет результаты в базу данных.

• Интегрирована работа с реальными камерами видеонаблюдения через API IS74, что позволяет использовать существующую инфраструктуру видеонаблюдения без необходимости установки дополнительного оборудования.

Система полностью удовлетворяет поставленным требованиям и обеспечивает:
• Автоматический сбор данных о пассажиропотоке с использованием компьютерного зрения;
• Предоставление актуальной информации о загруженности остановок в реальном времени (обновление каждую минуту);
• Построение прогнозов загруженности на основе исторических данных с учетом сезонности;
• Удобный веб-интерфейс для пассажиров и аналитические инструменты для транспортных компаний;
• Масштабируемую архитектуру, позволяющую обрабатывать данные с множества остановок;
• Эффективное хранение и обработку временных рядов с использованием TimescaleDB;
• Детекцию маленьких объектов на HD кадрах для точного подсчета людей;
• Распознавание номеров автобусов для идентификации транспорта.

**В перспективе система может быть расширена за счет:**
• Интеграции с системами распознавания номеров автобусов для более точной идентификации транспорта (улучшение алгоритмов OCR);
• Улучшения алгоритмов прогнозирования с использованием более сложных моделей машинного обучения (LSTM, Transformer, ARIMA);
• Разработки мобильного приложения для пассажиров с push-уведомлениями;
• Интеграции с системами управления транспортом для автоматической оптимизации маршрутов и расписания;
• Расширенной аналитики с использованием методов data mining для выявления паттернов пассажиропотока;
• Реализации системы уведомлений для пассажиров о приближении транспорта и текущей загруженности остановок;
• Трекинга людей между кадрами для более точного подсчета посадок и высадок;
• Интеграции с другими источниками данных (GPS-трекинг автобусов, данные о расписании);
• Реализации системы алертинга для транспортных компаний при превышении пороговых значений загруженности;
• Расширения функциональности для работы с другими видами транспорта (троллейбусы, трамваи).

Разработанная система демонстрирует эффективное применение современных технологий компьютерного зрения и машинного обучения для решения практических задач мониторинга общественного транспорта и может служить основой для дальнейшего развития информационных систем в сфере транспорта. Система успешно интегрируется с существующей инфраструктурой видеонаблюдения и предоставляет ценные данные для оптимизации работы общественного транспорта и улучшения качества обслуживания пассажиров.
